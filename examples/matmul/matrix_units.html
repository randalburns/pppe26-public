Matrix units: Apple, Intel, AMD and NVIDIA

Matrix multiply is so common, especially in machine learning, that chip makers now build hardware just for it. On this Apple M5, the built-in matrix unit multiplies matrices 18 times faster than our best code from Lecture 17.

Measured on this M5

Accelerate is Apple's math library. Its matrix multiply, sgemm, uses the matrix unit. The grey bars are our own kernels from Lecture 17, which use ordinary vector (NEON) instructions.

The idea: one instruction, hundreds of multiply-adds

A vector instruction on the M5 does 4 multiply-adds at once. A matrix instruction takes two vectors of 16 numbers and multiplies every number in one by every number in the other. That is 16 × 16 = 256 multiply-adds from one instruction, and only 32 numbers had to be loaded.

This is the register tiling from Lecture 17, built into the hardware. Our reg4x16 kernel kept a 4 × 16 block of the result in registers and updated all of it from a few loaded values. A matrix unit keeps a much bigger block of the result inside itself and updates it in one step.

Words you will see

FLOP/s, GFLOP/s, TFLOP/s
Floating-point operations per second: billions (G) or trillions (T). 1 TFLOP/s = 1,000 GFLOP/s.
FP32, FP64
Ordinary 32-bit and 64-bit floats: C's float and double.
FP16, BF16
Two 16-bit float formats. Half the memory of FP32, less precise. Common in machine learning, where the lost precision usually doesn't matter.
INT8
8-bit integers. Used to run trained neural networks cheaply.
Tile
A small matrix held in a special register inside the matrix unit.
NEON, AVX-512
The ordinary vector instructions on Arm and x86. NEON handles 4 floats at a time, AVX-512 handles 16.

In the CPU: three companies, three answers

Apple

A matrix unit in every Mac

  • Before 2024 (M1 to M3): the unit was called AMX and was secret. Apple didn't publish its instructions. Programs could use it only by calling Apple's libraries.
  • M4 and M5: the unit now uses SME, a public instruction set from Arm. Compilers can produce it and anyone can write code for it.
  • It handles ordinary 32-bit and 64-bit floats, as well as the smaller formats.
  • The cores share it. There is one unit for a group of cores, not one per core.

Available today. This M5 has it.

Intel

AMX, in server chips only

  • In Xeon server processors since 2023. Laptop and desktop Intel chips don't have it.
  • Every core gets its own unit: 8 tile registers and a multiplier for them.
  • It multiplies whole tiles: one instruction does up to 8,192 multiply-adds.
  • It doesn't take FP32. Inputs must be BF16, FP16 or INT8. It was designed for machine learning, not general math.

Available today on Xeon. The operating system has to switch it on for each program.

AMD

No matrix unit yet

  • AMD's processors have nothing like AMX. They use AVX-512 vector instructions, including some made for BF16 and INT8.
  • AMD puts its matrix hardware in its graphics cards instead.
  • ACE is a new matrix instruction set that AMD and Intel announced together in 2025. The goal is one design that works on both companies' future chips.

No processor with ACE has been announced as of late 2026.

How Intel's version works

Apple's unit multiplies two vectors. Intel's multiplies two small matrices. All three matrices sit in tile registers, and one instruction computes C += A × B for the whole tile. Each tile holds up to 1 KB of data.

NVIDIA

In the GPU: NVIDIA Tensor Cores

NVIDIA put matrix hardware in its graphics cards in 2017, before any of the CPU units above. Tensor Cores multiply two small matrices and add a third, D = A × B + C, in one step.

The sizes depend on the number format. With 16-bit floats, one step multiplies a 16 × 16 matrix by a 16 × 16 matrix. With TF32 (explained below), it is 16 × 8 times 8 × 16, written 16 × 16 × 8: a 16 × 16 result built from 8-term sums. With 64-bit floats it is 8 × 8 × 4. NVIDIA first described the 2017 hardware as a 4 × 4 unit; the sizes here are what one operation does on current GPUs.

The big difference from a CPU is the count. A CPU has one matrix unit, or one per core. A GPU has hundreds of Tensor Cores spread across the chip, all working at once. That is why GPUs dominate machine learning.

TF32 is worth knowing. Your program still stores ordinary 32-bit floats. The Tensor Core rounds each one to about 3 decimal digits of precision before multiplying, then adds up the results in full FP32. You get most of the speed of FP16 without changing your data. The answer is slightly less exact.

How fast

What it costs

  • The data has to be on the GPU. A GPU has its own memory. Copying matrices to it and back takes time, so small problems can be faster on the CPU.
  • The speed comes from smaller numbers. The best rates need FP16, BF16 or smaller. Full FP32 doesn't use Tensor Cores at all, and TF32 gives up some precision.
  • You mostly use it through libraries. cuBLAS and cuDNN use Tensor Cores for you. In PyTorch, turning on mixed precision (torch.autocast) is usually all it takes.

What it does to the roofline

The flat part of the roofline is the most arithmetic the processor can do. A matrix unit raises that roof on the M5 from 130 GFLOP/s to about 2,000. The slanted part, set by memory speed, doesn't move.

So a matrix unit only helps kernels that were limited by arithmetic. Matrix multiply is one: it does a lot of arithmetic per byte of data. Stencils, sparse matrix code and most other kernels from this course were limited by memory, and a matrix unit does nothing for them.

The lesson is the same as in Lecture 17: use each number you load as many times as you can. Register tiling did that with 16 registers. Matrix units and Tensor Cores do it in hardware.

How to use one

  • Call a library. This is what almost everyone does. Accelerate on a Mac, oneDNN or MKL on Intel, cuBLAS on NVIDIA. PyTorch and NumPy call these for you.
  • Write it yourself. Each one has C functions (intrinsics) that map to its instructions: arm_sme.h for Apple, immintrin.h for Intel AMX, and the WMMA functions in CUDA for Tensor Cores.
  • Expect a start-up cost. The CPU units have to be switched on before use, and a GPU needs its data copied over. Small matrices may not be worth it.

One operation is only part of the answer

Each element of a matrix product is a sum over all of k: C[i][j] = Σ A[i][k] · B[k][j]. For 1024 × 1024 matrices, that sum has 1,024 terms. No matrix unit adds all of them at once. One operation adds a few terms to every element of a small block of the result, and a loop repeats it until all of k is done.

UnitTerms of the sum added per operationResult blockOperations per block at n = 1024
Apple SME1 (one column of A times one row of B)16 × 161,024
NVIDIA Tensor Cores8 with TF32, 16 with FP1616 × 16128 or 64
Intel AMX32 with BF1616 × 1632

So the result block is updated many times. That is why every one of these designs keeps the block inside the unit, in a tile or in registers, and not in memory. The block is loaded once, updated for every k, and stored once.

This is exactly the loop from Step 5 of the lecture: acc stayed in registers while k ran from 0 to N. The hardware changes how much work one step of that loop does. It doesn't change the loop.

These repeated updates are not the costly kind from Step 6. There, several threads each held part of the sum and had to merge their results. Here one thread owns the block and adds the terms in order, so nothing has to be merged.
