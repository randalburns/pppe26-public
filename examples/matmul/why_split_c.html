Lecture 17, Step 6 · matrix multiply on several threads

Why split the output C, and not the inputs A and B

There are two ways to share a matrix multiply among threads. One gives each thread its own part of the answer. The other gives each thread its own part of the inputs. The first needs no coordination at all. The second makes every thread write to every part of the answer.

Two places to cut

Every number in C is a sum over k:

C[i][j] = A[i][0]·B[0][j] + A[i][1]·B[1][j] + … + A[i][n−1]·B[n−1][j]

There are n² of these sums, one for each (i, j), and each has n terms. To share the work we can hand out the sums, or hand out the terms.

  • Split the output. Each thread gets some of the (i, j): a band of rows of C. It computes each of its sums from the first term to the last.
  • Split the inputs. Each thread gets a range of k: a band of columns of A and the matching rows of B. It computes a few terms of every sum.

Who writes each number of C?

1. Nothing to synchronize

A race needs two threads using the same data, with at least one of them writing (Lecture 14). When the output is split, the threads share only A and B, and nobody writes those. Each number in C has one writer. So there are no locks, no atomics, and no thread ever waits for another.

Put another way, the threads have no dependencies on each other. No thread needs a result from another thread, so they can run in any order, at any speed, and still be correct.

2. Sharing reads is free. Sharing writes is not.

Splitting the output makes every thread read all of B. That sounds wasteful, but data that is only read can sit in every core's cache at once. Nothing ever has to be updated or handed over (Lecture 13).

Splitting the inputs avoids those repeated reads, and pays with repeated writes: every thread writes every part of C. When several cores write the same cache line, the line has to move from core to core, and each move takes far longer than the arithmetic. This is the true sharing from Lecture 13.

3. Every way of merging costs something

If the inputs are split, the pieces have to be combined. There are three ways to do it, and we measured all three.

  • An atomic add for every term. Safe, but there are n³ of them. Each is a small retry loop, and the compiler can't turn that into vector code. It is 12 times slower even with one thread.
  • Add up a whole row privately, then add it into C with atomics. Far fewer atomics. But each one has to wait for its cache line to arrive from whichever core wrote it last.
  • Give each thread a private copy of C, and add the copies at the end. No atomics. It costs a full extra copy of C for every thread (64 MB for n = 2048 on 4 threads), and every thread writes a whole matrix.

Private copies keep up, at the price of memory: four extra copies of C. Atomic-per-row is slower on 4 threads than on 2 at n = 1024 (64 against 69). Splitting the output matches the best of them and needs nothing extra.

It also gets worse with more threads. The merging work grows with the number of threads, while each thread's share of the multiply shrinks.

4. The same answer every time

Floating-point addition rounds, so adding the same numbers in a different order can change the last digits of the result.

5. Each thread gets a complete, smaller problem

A band of rows of C is a matrix multiply of its own: fewer rows, same columns, the whole of k. Everything from the earlier steps of the lecture works on it without change: the loop order, the tiling, the compiler flags. On the M5's 4 fast cores it runs 3.1–3.2 times faster than one core, and reaches 135–146 GFLOP/s with the tiled loop inside.

When splitting the inputs is right

Splitting the output only works if there is enough output to go around. Sometimes there isn't.

The rule: split the output for as long as that gives every thread enough work. Split the sum only when it doesn't.
