Register tiling: keep a block of C in registers

Our best loop so far, ikj, runs at 36 GFLOP/s on one M5 core. The core can do 130. Register tiling gets to 114 by changing one thing: where the results are kept while they are being added up.

Three terms, used the same way all the way down

  • A multiply-add is one c += a * b on single numbers. Matrix multiply at n = 1024 needs about a billion of them.
  • A register here is a NEON vector register. It holds 4 floats. The M5 has 32 of them.
  • An FMA is one instruction that does a multiply-add on a whole register: 4 multiply-adds at once.

Speeds are in GFLOP/s: billions of floating-point operations per second, where a multiply-add counts as two operations.

What slows down ikj

The inner loop of ikj is C[i][j] += a * B[k][j]. For every FMA it has to fetch 4 numbers of B, fetch 4 numbers of C, and write the 4 results back to C. That is 3 trips to memory for 1 FMA.

The core has the arithmetic units to go much faster. It is waiting on those loads and stores.

The idea

Pick a small block of C, here 4 rows by 16 columns, and keep it in registers for the whole k loop. C is loaded once before the loop and stored once after it. Inside the loop, C never touches memory.

Each step of k then needs only two things from memory: 4 numbers from a column of A, and 16 numbers from a row of B.

The arithmetic is the same. The memory traffic is six times smaller, because every number that is loaded gets used many times: each number of A in 16 multiply-adds, and each number of B in 4.

for (i = 0; i < N; i += 4)
    for (j = 0; j < N; j += 16) {
        float acc[4][16];                       // the compiler keeps this in 16 registers
        /* load acc from C: once */
        for (k = 0; k < N; k++)
            for (r = 0; r < 4; r++)
                for (c = 0; c < 16; c++)
                    acc[r][c] += A[i + r][k] * B[k][j + c];
        /* store acc to C: once */
    }

How big should the block be?

A block of R rows by C columns holds R × C numbers. A register holds 4, so the block needs R × C ÷ 4 registers. We tried eight shapes:

The speed follows the number of registers, not the shape. Blocks with 4 registers run at about 30, with 8 at about 60, with 16 at about 105. Then it gets worse. Two different limits explain the two sides.

Too few registers: the core runs out of things to do

Two facts about the M5's fast cores:

  • The core can start 4 FMAs every cycle.
  • An FMA takes about 4 cycles to finish.

An FMA that adds into a register needs that register's current value. So it can't start until the previous FMA into the same register has finished. Each register can therefore take one new FMA every 4 cycles.

With only 4 registers, the core starts 4 FMAs, then has nothing it is allowed to start for the next 3 cycles. With 16 registers there are always 4 that are ready.

That gives a prediction for each register count. The core's peak, 130 GFLOP/s, is what Lecture 16 measured with 4 FMAs starting every cycle.

The rule: registers needed = FMAs started per cycle × cycles each one takes = 4 × 4 = 16. This is the "independent chains" idea from Lecture 3. With 16 registers the prediction is the full 130 and we measure 105; the loads of A and B take the rest.

Too many registers: the block no longer fits

The M5 has 32 registers, and the block of C is not the only thing that needs them. The 16 numbers of B take 4 more, and A needs a few.

When the block doesn't fit, the compiler keeps part of it in memory and moves numbers in and out as it goes. That is the memory traffic we set out to remove, so the speed drops: 81 for 8 × 16, and 53 for 16 × 16.

Bigger matrices need cache tiling as well

At n = 1024, all of B is 4 MB and sits in the M5's 16 MB cache. Register tiling alone is enough.

At n = 2048, B is 16 MB and doesn't fit. Every block of C walks through all of B again, fetching it from main memory, and the speed drops to 65.

Tiling k (Step 3 of the lecture) fixes that: work on 64 values of k at a time, so the part of B in use is small and stays in the cache. Together the two reach 101.

Register tiling made the arithmetic fast enough that memory became the limit again. Cache tiling barely helped ikj. Now it is worth 1.5×.

On the roofline

Every kernel from the lecture does the same arithmetic on the same data, so they all sit on one vertical line. Register tiling is the first one to come close to the roof.

Check what the compiler did

We never told the compiler to use registers. We wrote a small local array, acc, and trusted the compiler to keep it in registers and use FMAs. Mostly it did. Once it didn't.

For the 8 × 8 block, the compiler chose to vectorize a different loop. The code it produced kept moving the block in and out of memory, and ran at 39 GFLOP/s instead of 107. One line telling it not to vectorize the k loop fixed it.

When a number looks wrong, look at what the compiler produced before explaining it some other way. In the assembly, the good 4 × 16 version has exactly 16 FMA instructions per step of k and nothing else touching memory.

What is still missing

The best kernel reaches 87% of the peak. Math libraries get closer by packing: copying the parts of A and B about to be used into small buffers, in exactly the order the inner loop reads them. They also write the inner block by hand, so the compiler can't get it wrong.

Hardware takes the idea further. A matrix unit keeps a much bigger block of C inside itself and updates all of it with one instruction.
